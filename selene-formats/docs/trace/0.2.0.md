# Trace protocol 0.2.0

Schema: [`../../schemas/trace/0.2.0.schema.json`](../../schemas/trace/0.2.0.schema.json)

## Documents

The schema accepts two top-level document shapes:

* `Trace` represents one emulation shot and contains an `events` array.
* `Traces` represents a collection and contains a `traces` array of
  unversioned `TraceData` objects.

Both top-level shapes carry `schema_version`. `TraceData` contains the same
`events` field as a standalone `Trace`, but does not repeat the collection's
version. To extract a member as a standalone `Trace`, attach the enclosing
`schema_version`. A collection may be empty, and its traces retain their given
order.

## Event ordering and sources

`events` is ordered by observation during one emulation shot. An event's
`source` identifies the stage that emitted it:

* `UserProgram`: `index` is that source's zero-based event index.
* `Runtime`: `start_time` and `end_time` are nanoseconds in the runtime's shot
  timeline.
* `ErrorModel`: `index` is that source's zero-based event index.
* `Simulator`: `index` is that source's zero-based event index, and
  `duration_ns` is the wall-clock duration spent in the simulator call.

Indices are meaningful within a source only. Consumers must preserve event
order and must not assume that sources have equal event counts.

Indices, qubit IDs, timestamps, and durations are non-negative JSON integers no
larger than `9007199254740991`, so they can be represented exactly by a
JavaScript `number`. Opaque-payload tags retain the full unsigned 64-bit range
and are encoded as canonical hexadecimal strings: a lowercase `0x` prefix
followed by one to sixteen uppercase hexadecimal digits, with no leading zeroes
except for `"0x0"`. For example, `"0x11A12517"` is a valid tag, and the maximum
is `"0xFFFFFFFFFFFFFFFF"`. Gate parameters and values in
`KeyValuePairPayload` may be signed.

## Encoding

`OpaquePayload.data` is base64url-encoded in JSON. Padding may be omitted;
unused bits in the final Base64 character must be zero. `KeyValuePairPayload` is for
interoperable, structured custom metadata; consumers that do not understand an
application-specific key should preserve it when they re-emit the trace.

Gate `params` are JSON booleans or numbers. Integer-valued numbers in gate
parameters and `KeyValuePairPayload` values (including arrays) must be between
`-9007199254740991` and `9007199254740991`, inclusive. This also applies to
integer-valued floating-point notation such as `1e20`, which is rejected.
Fractional numbers remain supported. Gate parameter interpretation is determined
by `gate_name`.

## Measurements and future results

`Measurement` records a measurement operation:

```json
{"kind": "Measurement", "qubit": 0, "measurement_type": "Leaked", "result_id": 42}
```

`measurement_type` is a non-empty string whose names are defined by Selene.
The current types are `Standard` and `Leaked`; the default is `Standard`.
`Leaked` means the measurement checks for leakage; it does not mean leakage
occurred. Readers and serializers preserve unfamiliar names.
`result_id` identifies the measurement's future result. IDs are scoped to the
runtime and shot, and are not qubit IDs. Selene preserves the IDs supplied by
its runtime. References apply within that scope; consumers must not join IDs
across shots. IDs from simulator operations belong to that operation's stage and
must not be assumed to identify runtime futures.

Measurements produced during emulation include a numeric result ID. The model
permits a missing or null ID for imported traces whose measurement identity is
unavailable. Such measurements cannot be joined to result events. The default
measurement type on imported data does not establish that leakage detection was
absent when the input did not record the type.

`FutureRead` records a user request to read a measurement result:

```json
{
  "source": {"kind": "UserProgram", "index": 7},
  "event": {"kind": "FutureRead", "result_id": 42}
}
```

Emit one `FutureRead` before each read attempt, including repeated reads and the
read performed by an eager measurement. Its `result_id` references the
measurement's future, not a qubit. Reading a future does not add a quantum
measurement operation to an extracted circuit.

`FutureResult` records the successful response to that request:

```json
{
  "source": {"kind": "Runtime", "start_time": 120, "end_time": 120},
  "event": {"kind": "FutureResult", "result_id": 42,
            "outcome": 2}
}
```

`result_id` and `outcome` are required. An outcome can be any JSON value: a
number, boolean, string, null, array, or object containing other JSON values.
Object keys are strings. Numbers must be finite; integer-valued numbers at any
nesting depth must lie between `-9007199254740991` and `9007199254740991`, inclusive.
The outcome field remains required when its value is null.

Measurement types define their outcome semantics. `Standard` uses integer `0` or
`1` for the computational-basis result. `Leaked` additionally uses integer `2` for
leakage. These meanings remain fixed. Extension types can define other result
shapes within the JSON value contract, for example:

```json
{
  "source": {"kind": "Runtime", "start_time": 120, "end_time": 120},
  "event": {"kind": "FutureResult", "result_id": 43,
            "outcome": {"parity": true, "confidence": 0.875}}
}
```

Determine the measurement type from the `Measurement` with the matching
`result_id` in the runtime trace. Adding measurement types and result shapes
within this contract does not require a new schema version.

Emit one result event per successful read, including repeated reads and the read
performed by an eager measurement. Failed reads retain their `FutureRead` but
emit no result event. If a read forces pending quantum operations to execute,
the `FutureRead` precedes those operations and its `FutureResult` follows them.
A future that is never read has no `FutureResult` event.

A result event has Runtime source with equal start and end times, giving it zero
duration. Its timestamp is the greatest end time of runtime batches processed so
far, or zero if none have been processed in the shot. This is the execution
frontier when the read returns, not the measurement completion time or a measure
of classical processing or result-delivery latency. Repeated reads may share a
timestamp. Event order resolves ties.

Schema and binding validation check structure, non-empty type names, JSON value
shapes, and numeric bounds. They preserve unfamiliar measurement types and
outcomes without interpreting them. They do not validate whether an outcome
matches its referenced measurement type or require a matching measurement in the
same document: traces may be filtered or split across stream files.

Consumers interpreting results must resolve references in the appropriate shot
and runtime scope and check the outcome against the measurement type's semantics.
For `Standard`, require integer `0` or `1`; for `Leaked`, require integer `0`, `1`,
or `2`. These semantic checks are separate from structural parsing and
serialization.

## Compatibility

Parsing helper functions accept schema 0.1.0 documents and versionless singular
traces and normalize them into the current model. Constructors and direct model
deserialization require the current schema version. They cannot reconstruct missing result
IDs or measurement types. Stream readers also accept schema 0.1.0 headers;
writers emit schema 0.2.0 with transport format version 1.

Versionless legacy serialization rejects `FutureRead` and `FutureResult`, which
are not part of the legacy event vocabulary. Use versioned serialization for traces with result reads.
